Agent 原理 · 第 3 课

上下文工程：对话变长之后

每个 turn 都要把全部历史发给模型，而模型的上下文窗口是有限的、按 token 收费的。学完这课，你能说清 aionrs 的三级压缩策略，并理解为什么「省 token」是生产级 agent 的核心成本线。

问题有多严重

回看第 1 课的循环：每个 turn 都把完整历史发给模型。一次读文件可能带回几千行，十轮工具调用下来，历史轻松突破几万 token。三个后果：

后果原因
变贵每个 turn 都为全部历史付费，成本随对话长度平方级增长
变慢首 token 延迟随输入长度上升
变笨长上下文里关键信息被淹没（"lost in the middle"），撞墙就直接报错
核心原则：上下文是 agent 最稀缺的资源。生产级 agent 不是「把一切都发给模型」，而是「每个 turn 只发此刻最有用的东西」。管理上下文 = 管理 agent 的注意力。

aionrs 的三级压缩（真实实现）

aionrs 的 compact 模块按严重程度分三级，逐级升级：

级别触发条件做法调用 LLM？
Microcompact工具结果数量超阈值，或离上次压缩时间太久清空旧的工具结果内容，只保留最近 N 条否（零成本）
Autocompact输入 token 接近上下文上限让 LLM 把整段对话总结成摘要，带着摘要继续是（花一次钱）
Emergency输入 token 逼近绝对上限阻止继续调用 API，请用户开新会话否（直接拒绝）
📄 真实代码：aion-agent/src/compact/mod.rs（模块头注释就是这张表）；官方说明在 docs/advanced.md 的 Context Compression 一节

为什么是这个顺序

三级策略体现一条通用的工程设计原则：先用便宜的手段，不够再升级。

第一级最精妙：工具结果（文件内容、命令输出）是历史里体积最大、时效最短的部分——模型用完一次就很少再需要原文。清掉它们不调 LLM、不花一分钱，却能腾出大半空间。第 2 课讲的 Read 文件缓存（「文件没变，看之前的」）也是同一思路：不重复发送。

第二级才动用 LLM 做摘要——准确但有成本有延迟。第三级是兜底熔断：宁可停下来请用户开新会话，也不让请求带着超限的上下文白白失败。

还有一条腿：持久记忆

压缩解决「单次对话太长」，但跨会话怎么办？aionrs 的 aion-memory crate 做项目级持久记忆：把值得长期记住的东西（项目约定、用户偏好）存下来，新会话自动索引注入。压缩是「忘得聪明」，记忆是「记住该记的」——方向相反，目标相同：让模型每个 turn 看到的都是高价值内容。
