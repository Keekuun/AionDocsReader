Agent 原理 · 第 2 课

工具：Agent 的手和眼

上一课的循环里，模型说「我要读文件」就能读到文件——靠的就是工具。学完这课，你能说清工具是怎么被模型发现和调用的，并能自己设计一个工具。

先纠正一个直觉

模型从来不会「执行」任何东西。它只是输出一段结构化文本（tool_use）：「我想调用 Read，参数是 {file_path: "..."}」。真正读文件的是引擎。工具调用 = 模型的请求，不是模型的动作。

工具的三张名片

模型做选择时，看到的只有每个工具的三样信息。aionrs 里每个工具都实现同一个 Tool trait：

pub trait Tool {
    fn name()        → "Read"            ← 名片①：名字
    fn description() → "Reads a file..." ← 名片②：说明书
    fn input_schema() → JSON Schema      ← 名片③：参数格式

    async fn execute(input) → ToolResult  ← 模型看不到，引擎用
}
📄 真实代码：~/.cargo/git/checkouts/aionrs-c860c928cccf810e/8e61a90/crates/aion-tools/src/tool.rs 第 44 行

每个 turn 开始时，引擎把注册表里所有工具的三张名片打包进请求（engine.rs 第 688 行的 to_tool_defs_filtered）。模型的全部依据就是这些名片。

说明书是写给模型的 prompt

看 Read 工具 description 的真实原文（节选）：

"Reads a file from the local filesystem. Returns content with line numbers.
 Usage:
 - The file_path parameter must be an absolute path, not a relative path.
 - By default, it reads the entire file. Use offset and limit for partial reads..."
📄 真实代码：aion-tools/src/read.rs 第 39 行
这是本课最重要的洞察：description 不是写给人类看的注释，而是随请求发给模型的操作说明书。「必须用绝对路径」这句话直接塑造模型的行为。写工具 = 写代码 + 写给模型看的 prompt，两者同样重要。你以后设计自己的 agent 工具时，一半功夫在 description 上。

工具注册表：引擎的花名册

ToolRegistry 就是一个列表：启动时把工具一个个 register 进去；模型点名时按名字 get 出来执行：

registry.register(ReadTool::new(...));
registry.register(WriteTool::new(...));
registry.register(ExecCommand::new(...));
// ... Grep / Glob / ViewImage / Spawn / ToolSearch

// 每个 turn：名片打包进模型请求
let defs = registry.to_tool_defs();
// 模型点名后：按名字找到并执行
let tool = registry.get("Read")?;
📄 真实代码：aion-tools/src/registry.rs（整个文件只有 60 行，值得通读）

你来当一次模型（交互）

场景：用户说「看下 Cargo.toml 前 50 行」。你现在就是模型，手边有三张工具名片。做出你的选择：

第 1 步 · 选工具

三个工具的 description 大意如下，选哪个？

第 2 步 · 填参数

你选了 Read。回看它的说明书：「file_path must be an absolute path」。填哪个？

引擎执行

引擎从注册表取出 Read，校验参数，读文件，结果以 User 角色写回历史，进入下一 turn：

tool_result: "1→[workspace]\n2→resolver = \"3\"\n3→members = [..."
// history += [Assistant(tool_use), User(tool_result)]
// 下一 turn：模型基于文件内容给出最终解释

🎉 你刚刚以模型的视角完成了一次完整的工具调用。

MCP：外部工具怎么进来

MCP 服务器（比如「查数据库」「操作 Figma」）的工具不在这个仓库里。aionrs 的做法是包一层代理：McpToolProxy 实现同一个 Tool trait，execute 里转发给远程服务器。命名冲突时加前缀 mcp__{服务器}__{工具}。

📄 真实代码：aion-mcp/src/tool_proxy.rs
设计要点：对模型来说，MCP 工具和内置工具长得一模一样——都是三张名片。这就是好抽象：新增能力不改循环，只往注册表里加工具。你自己造 agent 时，这条「一切能力皆工具」的原则直接照抄。

小测验（即时反馈）

🎉 三题全对。你已经理解工具系统的设计——去做动手任务吧。

动手任务（15 分钟）

通读一个真实工具的全部源码

1. 打开 aion-tools/src/read.rs（约 180 行，路径见上面 file-ref）。

2. 找到四个东西：description 全文、input_schema 的 JSON、execute 里参数缺失时的返回、文件缓存的去重逻辑。

3. 顺手打开同目录的 write.rs，对比它的 is_concurrency_safe 返回了什么。

✓ 完成标志：能回答两个问题——① 模型没传 file_path 时工具返回什么（一个 is_error=true 的 ToolResult，错误信息也是写给模型看的，它会据此自我纠正）；② Write 的 is_concurrency_safe 为什么是 false。
