Agent 原理 · 第 5 课

会话与持久化：关掉窗口，对话还在

前几课的循环和工具都活在内存里。但真实产品要能关掉重开、崩溃恢复、甚至「分叉」出一条平行对话。学完这课，你能说清 session 的存取模型和几个容易踩的坑。

内存里的历史 ≠ 能恢复的会话

第 1 课的循环维护一个 messages 数组，进程一退就没了。生产级 agent 需要：写到磁盘、按 ID 找回、崩溃后能恢复、还能从某个历史点「分叉」出新对话。aionrs 的 SessionManager 负责这件事。

写入时机：每个关键动作后立刻落盘

回看第 1 课的循环代码，注意一个当时略过的细节：push_history 之后几乎总是跟着 save_session()——

// 用户输入落盘
push_history(User, input);   save_session();

// 模型的工具调用落盘
push_history(Assistant, calls); save_session();

// 工具结果落盘
push_history(User, results); save_session();
📄 真实代码：aion-agent/src/engine.rs 的 run_inner（第 514 行的循环内部）
设计原则：崩溃发生在任何一行，丢的都不超过一步。不是「结束时统一保存」，而是「每步都保存」。写盘很便宜，丢上下文很贵——agent 的会话里每个 token 都是花钱买来的。

SessionManager 的四个操作

操作干什么细节
create新会话记录 provider、模型、工作目录
save落盘先拿会话级文件锁再写（with_session_lock）
load找回支持 "latest"；旧格式自动迁移后另存
fork分叉复制历史成新会话，记录 lineage 但不跟随
📄 真实代码：aion-agent/src/session.rs（SessionManager，约 200 行）

三个容易踩的坑（都是真实代码里的对策）

① 并发写同一会话。两个进程同时写一个 session 文件会写出损坏的 JSON。aionrs 的对策是文件锁：save 先抢锁再写。你在 AionCore 也见过同款设计——数据目录的 instance guard（「another aioncore already owns this data directory」）。

② 格式演进。软件升级后 session 文件格式变了，旧文件不能丢。load 里先尝试当前格式，失败再走 legacy 加载，成功后立刻按新格式另存——读取路径里顺手完成迁移。

③ 分叉的血统。fork 出来的会话记录自己从哪来（lineage），但加载时绝不顺着 lineage 去找父会话——那只是元信息，不是引用。否则父会话被删，子会话就打不开了。

亲手验证（交互 + 真实文件）

你的电脑上就有真实的 session 文件。aionrs 把会话存在用户目录下（AionUi 的对话则存在 AionCore 的 SQLite 里——两种持久化选型，第 7 课你会自己权衡）。

想一想：aionrs 用「每会话一个 JSON 文件」，AionCore 用 SQLite 表。各自适合什么场景？文件：简单、可查看、易备份，但不擅长跨会话查询。SQLite：支持搜索、关联、分页（你在第 7 课的动手任务里见过 /api/messages/search），但要管理迁移。没有银弹，只有权衡。
