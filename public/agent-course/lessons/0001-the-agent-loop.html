Agent 原理 · 第 1 课

Agent 循环：一切 Agent 的最小内核

学完这一课，你能用一句话说清任何 AI Agent 在干什么，并能在 aionrs 的真实源码里找到那个循环。

一句话原理

Agent = 一个 while 循环。把对话历史发给模型 → 模型要么给出最终答案（循环结束），要么要求调用工具 → 引擎执行工具、把结果塞回历史 → 再发给模型……直到模型说「答完了」。

Claude Code、Codex、Cursor Agent、aionrs——外壳千差万别，内核都是这一个循环。所谓「生产级」，是在这个循环上加护栏、上下文管理和权限，我们后面几课逐个拆。

四个运行时单位（背下来）

aionrs 官方文档把一次任务拆成四层。这套术语后面每课都用：

单位含义类比
Run一次用户提问，从 stream_start 到 stream_end一通完整的客服电话
Turnrun 里面的一次模型往返：发请求、收流式响应电话里的一问一答
Tool round一个 turn 里模型要求的那一批工具调用（0 或 1 次）客服放下电话去查资料
Tool call / result一次工具调用和它对应的结果，成对出现查一次资料、记一条笔记

数量关系：run 1:N turn，turn 0:1 tool_round，tool_round 1:N tool_call。

真实代码里的循环

aionrs 的循环在 engine.rs 的 run_inner 函数里。删掉细节后，骨架就是这么点：

loop {
    // 护栏：超过轮次预算就停，报告「没收敛」
    if guards.turn_budget_reached() { return MaxTurns; }

    // 一个 turn：把历史发给模型，收流式响应
    let outcome = run_turn().await?;

    match outcome {
        // 模型给了最终答案 → 写入历史，run 结束
        Final(text)   => { push_history(Assistant, text); return Done; }
        // 模型要调工具 → 执行这一批，结果写回历史，继续循环
        ToolRound(calls) => {
            push_history(Assistant, calls);
            let results = execute_tool_round(calls).await?;
            push_history(User, results);   // ← 结果伪装成 User 消息
        }
    }
}
📄 真实代码：~/.cargo/git/checkouts/aionrs-c860c928cccf810e/8e61a90/crates/aion-agent/src/engine.rs 第 514 行的 loop
注意一个反直觉的细节：工具结果是以 User 角色写回历史的，不是 Assistant。因为对模型来说，「工具返回的内容」就是新的输入。这是所有工具型 agent 的通用做法。

模型 · Turn 2

历史里现在有文件内容了。模型决定：「信息够了」。

返回最终文本：「这个 workspace 有 12 个 crate……」
引擎

最终答案写入历史，发出 stream_end，run 结束。

本次 run：2 个 turn，1 个 tool round，2 对 tool call/result
第 1 / 5 步

生产级的第一块砖：护栏

玩具 agent 和生产 agent 的第一个分水岭，藏在刚才那个循环的 guards 里。真实代码里每个 run 都带着这些防护：

护栏防什么
max_turns模型陷入工具死循环，把 token 预算烧光
malformed 重试上限模型输出格式坏掉的工具调用，无限重试
empty-final 重试模型把工具调用藏在「思考」里，正式回答却是空的

没有护栏的循环，线上跑一次死循环就是一笔真金白银的账单。这就是为什么第 6 课会专门讲防护与停止条件。

深入一层：循环里面还有一条事件流

到目前为止我们把一个 turn 看成「发请求、等响应」的黑盒。实际上 turn 内部是流式的：模型每生成一小段，引擎就发一个事件给客户端。你在 AionUi 里看到的打字机效果，就是这条事件流驱动的。

aionrs 的引擎和客户端之间有一份完整的事件协议（ProtocolEvent 枚举），一次 run 的真实事件序列长这样：

StreamStart                        // run 开始
Thinking { "我先看看文件..." }      // 模型的思考（可折叠展示）
ToolRequest { tool: "Read" }       // 模型要调工具了（界面显示卡片）
ToolRunning { tool_name: "Read" }  // 引擎开始执行
ToolResult  { status: "ok", output }// 执行完毕
TextDelta { "这个 workspace " }     // 最终答案的流式片段
TextDelta { "有 12 个 crate..." }
StreamEnd { usage }                // run 结束，附带 token 用量
📄 真实代码：crates/aion-protocol/src/events.rs 的 ProtocolEvent 枚举（共 14 种事件，含 ToolCancelled / Error / McpReady）

注意 Thinking 和 TextDelta 是分开的两种事件：思考过程和正式回答走不同通道，界面才能把思考折叠起来。另外每个 turn 结束还有一个 StopReason 四选一：EndTurn（答完了）/ ToolUse（要调工具）/ MaxTokens（输出撞上限）/ MaxTurns（护栏熔断）——循环就是靠它决定下一步。

📄 真实代码：crates/aion-types/src/message.rs 第 208 行
为什么值得懂：你以后给自己的 agent 加界面时，第一件事就是设计这条事件流。流式不是锦上添花——没有它，用户盯着死等的空白 30 秒，会以为程序死了。
